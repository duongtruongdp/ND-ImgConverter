# M4.1-WIN-P0 — Windows installed media-engine resolver hotfix

Status: source fix implemented; native Windows installed-app acceptance pending.

## Root cause

The v0.9.0 bundled resolver built paths from `current_exe().parent()` using
`resources/binaries/<name>` and a few legacy parent paths. It did not treat the
Tauri `resource_dir()` or the executable directory itself as a first-class
resource root.

The confirmed NSIS layout is:

```text
<install directory>\ND Image Converter.exe
<install directory>\binaries\ffmpeg.exe
<install directory>\binaries\ffprobe.exe
<install directory>\binaries\yt-dlp.exe
<install directory>\binaries\gallery-dl.exe
<install directory>\binaries\bgutil-pot.exe
```

Therefore v0.9.0 could report “no bundled executable was found” even though
all five executables were present and independently healthy. The old resolver
also allowed an extensionless fallback after the `.exe` name on Windows.

## Fix

- Initialize the resolver with Tauri `resource_dir()`.
- Search the authoritative resource directory and executable directory before
  legacy `resources/` variants.
- Use only canonical `.exe` bundled names on Windows; extensionless files are
  not selected as bundled Windows engines.
- Keep managed → bundled → explicit development fallback precedence.
- Keep system PATH fallback disabled for production builds.
- Record OS, architecture, executable/resource directories, every candidate
  path, existence, selected path, source and health result in the runtime probe
  and diagnostics payload.
- Bound version and FFmpeg capability checks to ten seconds and distinguish
  missing, launch, timeout and health-check failures.
- Invalidate the diagnostic cache during runtime initialization.

## Before/after reproduction

The Rust regression test creates the installed layout at `<root>\binaries`,
asserts that the v0.9.0-style `resources/` search misses it, then asserts that
the fixed root-first candidate list finds it. The test does not execute a fake
engine and does not alter verified runtime binaries.

The native release workflow now also launches the installed application with
`--nd-runtime-inventory`. That probe calls the same `engine_update::inventory()`
path used by the About → Media Engines UI and fails unless all five engines are
`available`, `bundled`, inside the installed directory, and resolved to `.exe`
files.

## Acceptance boundary

The source-side regression is validated locally on macOS. The required proof
that the old v0.9.0 NSIS installer fails and the fixed installer passes must run
on a native Windows runner after this change is pushed. Until that job passes,
the application version remains `0.9.0`, the existing `v0.9.0` tag/installers
remain untouched, and no `v0.9.1` release is published.
