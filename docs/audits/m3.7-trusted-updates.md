# M3.7 Trusted Engine Updates and Release Candidate Validation

Date: 2026-11-01

## Gap at start

- Update UI: implemented in M3.6.
- Ed25519 verification, staging, health checks, atomic activation and rollback: implemented in M2-M3.6.
- Verified publisher tooling: missing.

## Completed in M3.7

- Added `scripts/sign-engine-manifest.mjs`, which signs the existing schema with the exact Rust canonical field order and never writes or logs a private key.
- Added `scripts/prepare-engine-manifest.mjs`, which only accepts the approved target records in `runtime-sources.json`, hashes the actual five runtime artifacts, records companion compatibility, and emits the existing schema.
- Required a configured stable `ND_ENGINE_UPDATE_KEY_ID`; unknown key IDs now fail closed.
- Serialized engine downloads with a process-level async mutex and made the install IPC command derive the active media-job count in the backend instead of trusting the UI.
- Re-verified the exact signed manifest asset before download and again before install.
- Added publisher canonical-signature tests, modified-field rejection tests, real-binary installation/rollback coverage, and the M3.7 configuration/custody instructions.
- Changed the empty downloader queue copy to “No downloads yet.” without changing the M3.6 layout.

## Real artifacts

The local workstation contains approved authentic macOS arm64 runtime binaries. The ignored real-binary test uses the bundled `yt-dlp` and the separately installed Homebrew `yt-dlp` only when both are available; it verifies executable health, managed version reporting, activation, and rollback. It is not production publishing evidence.

## Remaining gates

- Production Ed25519 key must be generated and stored in protected release infrastructure.
- Immutable artifact/manifest hosting must be authorized and deployed.
- A signed app build must embed/configure the production public key and stable key ID.
- Windows x64, macOS arm64, and macOS x86_64 packaged update acceptance must run on their native CI/clean machines.
- Real media-operation-after-update and platform signing/notarization/AuthentiCode acceptance remain release gates.

## Trust boundary

Signature and hash checks authenticate the publisher metadata and downloaded bytes. They do not sandbox a native executable, prove the upstream build process is benign, or replace OS code-signing/reputation controls. The app still relies on runtime health checks, managed-directory permissions, HTTPS/host controls, and platform security.
